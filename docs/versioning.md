# 版本与发布维护

一个迭代应能够对应到明确的代码提交、变更说明和可复现产物。Git 用于记录过程，Tag 固定发布提交，Release 说明用户能获得什么以及使用边界。

## 版本约定

- `v1.0.0`：首次公开源码与合成演示基线。
- `v1.1.0`：向后兼容的功能增加。
- `v1.1.1`：向后兼容的问题修复。
- `v2.0.0`：需要使用者调整配置、接口或数据结构的不兼容升级。

应用版本和资料年份分别维护。`v1.0.0` 不代表 2026 年所有招聘事实已完整核实，也不表示下一届资料已经发布。

## 日常迭代

1. 从当前主分支创建用途明确的分支，例如 `fix/province-ranking-scope`。
2. 将一次可解释的改动写成提交，避免把源码、私有资料和构建缓存混在一起。
3. 在 Pull Request 描述实际问题、修改后行为及验证范围。
4. 合并前检查类型、构建、演示合同，以及改动涉及的交互路径。
5. 更新 `CHANGELOG.md` 中的未发布记录。

历史版本以真实的 Git 提交与 Tag 固定；不要用重新上传同名 ZIP 替换历史而不记录差异。

## 发布一个版本

1. 确定发布提交，确认工作区未包含未记录的必要改动。
2. 在干净环境安装锁定依赖，运行公开验证命令。
3. 检查源码、压缩包、图片、日志和文档中的凭据及私有数据。
4. 更新版本记录，创建带说明的 Tag，再创建指向该 Tag 的 Release。
5. 为附加包生成 SHA-256 校验文件，说明它是源码包还是已构建资源。
6. 从 GitHub 下载一次发布包，核对校验值并复验关键启动步骤。

Release 正文应包含本版亮点、使用方法、变化、已知限制，以及数据/许可边界。没有实际完成的检查不能写为通过。

## 运行版本与恢复

部署记录至少包含应用 Tag/提交、数据版本、迁移状态、部署时间和关键验证结果。配置与秘密由运行环境管理，不写入版本库。

应用产物回滚与数据库恢复分别设计。已迁移的数据结构或用户写入不应被盲目覆盖；恢复流程需要在独立环境演练。仓库的通用示例不包含任何线上环境的私有恢复指令。
